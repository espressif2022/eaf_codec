# EAF 统一压缩规范与 565 / 8888 支持矩阵 (`0x00 ~ 0x07`)

本仓库将原有的 `RGB565 / RGB565A8` 与 `BGRA8888` 方案彻底收拢为一套 **连续无空洞的 8 项编码 ID (`0x00 ~ 0x07`)**：其中 `0x00 ~ 0x03` 保持与历史老资产 100% 字节兼容，**`0x04 ~ 0x07` 为正式收敛的 4 大正交生产主力**。`RGB888` 当前仅保留枚举，不作为已实现输出格式。

> 本文保留算法与硬件加速速查。像素位数、Straight Alpha、Color-Key、
> “BGRA 输出但不携带 Alpha”等语义，以
> [《色深、输出格式与透明度》](EAF_COMPRESSION_MODES_GUIDE.md#3-色深输出格式与透明度)
> 为统一说明。

---

## 一、统一编码表与 565 / 8888 支持边界声明

| 编码 ID | 模式名 | 核心算法 | 565 格式 (`RGB565 / 565A8`) | 888/8888 格式 (`RGB888 / BGRA8888`) | 透明度支持声明 |
| :---: | :--- | :--- | :--- | :--- | :--- |
| **`0x00`** | `PALETTE_RLE` | 4/8-bit 调色板 + RLE | 支持（降采样为 `565+A8`） | **8-bit 原生支持**（调色板存的就是 32-bit `BGRA8888`，直接查表直写） | 支持 8-bit 调色板 Alpha |
| **`0x01`** | `PALETTE_HUFF_RLE` | 4/8-bit 调色板 + Huffman + RLE | 支持（降采样为 `565+A8`） | **8-bit 原生支持**（32-bit `BGRA8888` 直出） | 支持 8-bit 调色板 Alpha |
| **`0x02`** | `JPEG_KEYFRAME` | 标准整幅 JPEG（兼作 `0x06` 第 0 帧表头） | 支持（S31/P4 硬解 `hb` 对齐 + 软解） | 不支持（当前后端原生输出 RGB565） | **不支持 Alpha**（仅不透明底图/关键帧） |
| **`0x03`** | `PALETTE_HUFF` | 4/8-bit 调色板 + 直接 Huffman | 支持（降采样为 `565+A8`） | **8-bit 原生支持**（32-bit `BGRA8888` 直出） | 支持 8-bit 调色板 Alpha |
| **`0x04`** | **EAF Lossless** (`LOSSLESS`) | **100% 逐比特无损**（首帧独立压缩，帧间 `4×4` 变化块位图 + 平面/32-bit字XOR/81态三进制联合符号自适应） | **原生支持** (`RGB565 + A8`) | **原生支持** (`BGRA8888`) | **完整 8-bit 连续无损 Alpha** |
| **`0x05`** | **EAF Bounded** (`BTC_SAFE`) | **空域有界误差色胞**（`4×4` Skip / Flat / 2色 / 4色线性插值 + 原始逃逸块，锁死 $\text{maxErr} \le 8$） | **原生支持** (`RGB565` + 32B 逃逸块) | **原生支持** (`BGRA8888` + 64B 逃逸块) | **8888 原生支持四通道 8-bit Alpha**<br>565 仅支持不透明或 1-bit Color-Key |
| **`0x06`** | **EAF JPEG Delta** (`QUAD_JPEG`) | **频域变化块抽条带 JPEG**（`16×16` 宏块 + `8×8` 四象限掩码，变化块拼成 `height=16` 的 1D 条带 Abbrev-JPEG） | **原生支持** (`RGB565`) | 不支持（不做 RGB565→8888 扩色） | **不支持 Alpha**（JPEG 频域不支持透明通道，仅用于不透明自然光影/实拍动画） |
| **`0x07`** | **EAF Video** (`H264`) | **极限体积视频流**（Constrained Baseline Annex-B I/P 帧） | **原生支持** (`I420 -> RGB565` 查表) | **支持** (`I420 -> BGRA8888`，`A=255`) | **不支持 Alpha**（YUV420 视频流仅用于不透明全屏动画） |

## 二、关于 `0x06 EAF JPEG Delta`（`QUAD_JPEG`）与硬件 JPEG 加速说明

1. **为什么保留并对齐硬件 JPEG**：
   - 在无透明通道的自然光影、柔光渐变、相机实拍类动画中，`0x06 EAF JPEG Delta` 通常比有界误差或无损模式更小；具体比例必须以公开素材或目标业务素材实测为准。
2. **ESP32-S31 / ESP32-P4 硬件 JPEG 2D-DMA 宏块宽度对齐机制**：
   - S31 / P4 的硬件 JPEG 引擎通过 2D-DMA 输出时，水平方向必须按固定宏块宽度 `hb` 对齐（`YUV420/422` 下 `hb = 32 px`，`YUV444` 下 RGB888 `hb = 40 px`、RGB565 `hb = 48 px`）。若条带宽度不整除 `hb`，硬件 DMA 会超时或写越界。
   - **编码端已内置自动对齐**：`encoder/eaf565.py` 与 `encoder/quad_jpeg.py` 在将变化的 `8×8` 块打包为 `16×16` MCU 条带时，自动将 MCU 数量向上补齐到 `2`（`32 px`，对应 4:2:0/4:2:2）或 `3`（`48 px`，对应 4:4:4）的整数倍。
   - **解码端安全门卫**：`src/codec/common/esp_eaf_codec_support.c` 中的硬件 JPEG 后端调用 `jpeg_decoder_get_info()` 实时校验 `w % hb == 0 && h % 16 == 0` 且缓冲区 Cache Line 对齐后才启动硬件加速，否则无缝回退软件解码。
